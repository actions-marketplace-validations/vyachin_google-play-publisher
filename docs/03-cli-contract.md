# 03 — CLI contract

This document fixes the external interface: commands, flags, exit codes and output formats.
It is a contract for CI and for future implementation; do not change it without updating this
document.

## 1. General rules

- One binary: `google-play-publisher` (module `github.com/vyachin/google-play-publisher`).
- `stdout` carries the result (data); `stderr` carries logs and diagnostics. In JSON mode
  `stdout` contains **only** a single JSON object.
- A failure to write the human-readable result is itself an error and returns a nonzero code.
  When the primary outcome is more specific, it keeps its code and the write failure is added
  to the message: a release saved for manual submission stays 8, and `doctor` keeps the code
  of the failed check.
- Exit codes are stable, see §4. CI makes decisions on codes, not on message text.
- Secrets never appear in output or logs.
- Commands are idempotent in the described sense: a rerun after success is a no-op
  (`--if-exists=skip`) or a clear error.

### Global flags

Root-command flags (cobra `PersistentFlags`) apply to every subcommand and are accepted before
or after the command name: `google-play-publisher --debug publish ...` is equivalent to
`google-play-publisher publish --debug ...`.

| Flag | Type | Default | Description |
| --- | --- | --- | --- |
| `--debug`, `-d` | bool | `false` | Detailed logging to `stderr` (HTTP, retries, error bodies) |
| `--json` | bool | `false` | Machine-readable result on `stdout` |
| `--log-format` | enum | `text` | `text` \| `json` — log format on `stderr` |
| `--timeout` | duration | `20m` | Overall operation deadline |
| `--credentials` | path | ADC | Path to the JSON key; takes precedence over ADC |
| `--endpoint` | url | prod | For `httptest`-based tests |

## 2. Commands

Command tree (cobra), grouped for a readable `help`:

```
google-play-publisher
├── publish      Release
├── rollout      Release
├── promote      Release
├── doctor       Inspect
├── pull         Inspect
├── status       Inspect
├── version
└── completion   (generated by cobra)
```

`google-play-publisher completion bash|zsh|fish|powershell` and
`google-play-publisher help` are available without extra code.

### `google-play-publisher publish`

Uploads an AAB, declares the release on a track and commits. The default track is `internal`;
`rollout` and `promote` manage the other tracks without uploading another bundle.

```
google-play-publisher publish --package com.example.app \
  --aab app/build/outputs/bundle/release/app-release.aab \
  --track internal
```

| Flag | Type | Default | Description |
| --- | --- | --- | --- |
| `--package`, `-p` | string | from the AAB | `applicationId`; optional, but must match the AAB when supplied |
| `--aab`, `-f` | path | — | Path to the signed AAB; required |
| `--track`, `-t` | string | `internal` | Track name; the MVP uses `internal` |
| `--status` | enum | `completed` | `completed` \| `draft` \| `inProgress` (`inProgress` requires `--rollout`) |
| `--rollout` | float | `0` | User fraction, `0 < f < 1`; implies `inProgress` when `--status` is omitted |
| `--metadata-dir` | path | — | Play-style metadata tree: listings, images, testers and `changelogs/<versionCode>.txt` applied in the same edit; a changelog-only tree is accepted |
| `--version-code` | int | from the AAB | Optional assertion checked against the AAB and the upload; selects the changelog file with `--metadata-dir` |
| `--release-name` | string | — | Release name stored in Play; empty lets Play generate it from the AAB version name |
| `--changes-not-sent-for-review` | bool | `false` | Save changes without submitting them for review |
| `--on-in-review` | enum | `error` | `error` → `ERROR_IF_IN_REVIEW`; `replace` → `CANCEL_IN_REVIEW_AND_SUBMIT` |
| `--if-exists` | enum | `fail` | `fail` \| `skip` — behavior when the version code is already on the track |
| `--dry-run` | bool | `false` | Full run without `commit`, then delete the edit |
| `--in-app-update-priority` | int | `0` | In-app update priority, `0` (disabled) … `5` (highest); cannot change once a release is rolled out |
| `--country` | list | — | Restrict the release to CLDR country codes (repeatable, `DE` or `DE,FR`); only for an `inProgress` release on `production` |
| `--include-rest-of-world` | bool | `false` | Also target every country not listed in `--country`; requires at least one `--country` |

Release notes come from `--metadata-dir` when it is passed. The version code is read from the
AAB base manifest; a locale without `<versionCode>.txt` is skipped, so a partial translation is
allowed. A directory may contain only `changelogs/` or only listings/images/testers; when it
contains neither store metadata nor a changelog for the AAB version code, the command fails with
exit code 2 before any edit is created. `--version-code` is an optional assertion: when supplied
it must equal the AAB version code, and the uploaded bundle is checked against it.

The release identity comes from `base/manifest/AndroidManifest.xml`: `package`,
`android:versionCode` and `android:versionName`. The tool rejects a malformed or incomplete
manifest, resource-referenced values and a non-zero `android:versionCodeMajor` with exit
code 2 before authentication. `--package` and `--version-code`, when supplied, are assertions
against those values.

The remaining flags (`--debug`, `--json`, `--log-format`, `--timeout`, `--credentials`,
`--endpoint`) are global, see §1.

Combination validation (exit code 2 on violation):

- `--rollout` set, `--status` not set → status `inProgress`;
- `--rollout` together with an explicit `--status=completed` or `--status=draft` → error;
- `--status=inProgress` without `--rollout` → error;
- `--rollout` outside `(0,1)`, including `NaN` and infinities → error;
- `--version-code` different from the AAB version code → error;
- `--package` different from the AAB package → error;
- `--changes-not-sent-for-review` together with `--dry-run` → error;
- `--in-app-update-priority` outside `0..5` → error;
- `--country` that is not a two-letter CLDR code, or `--include-rest-of-world` without
  `--country` → error;
- country targeting on anything other than an `inProgress` release on `production` → error.

Country codes are normalized to upper case, de-duplicated and sorted, so `--country de --country
FR` sends `["DE","FR"]`. Play accepts `countryTargeting` only for `production` releases with
status `inProgress`; the tool enforces the same rule locally so the mistake costs no edit.

Dry-run success is reported only after edit deletion succeeds. If validation succeeds but
deletion fails, the command returns the cleanup error's exit code and identifies the edit
that may still exist; it does not print a successful validation result. Cleanup failures
after an earlier upload or validation error do not replace that original error. A signal
after validation keeps the edit (no delete request is sent) and returns 130; the dry run is
not reported as successful.

`--dry-run` is not "do nothing": the AAB is actually uploaded, the edit is validated and then
deleted. With `--metadata-dir` the listings, images and testers are applied to the edit before
validation as well, so a dry run exercises the same requests as a real release. It consumes
traffic, creates an edit (daily quota) and the uploaded `versionCode` may stay used even after
the edit is deleted. Never dry-run the version code reserved for a release. The output states
this explicitly.

Local validation (AAB and manifest identity, package, track, status, rollout, notes, metadata
and policy options) happens before the API client is created, so invalid input returns code 2
even when credentials are unavailable. The AAB is opened once; the inspected bytes are the
bytes uploaded.

### `publish --metadata-dir` — store metadata in the same edit

`--metadata-dir DIR` reads a Play-style metadata tree and applies store listings, images and
tester groups **in the same edit as the AAB**, so one commit publishes the bundle and the
metadata together:

```
metadata/
  en-US/
    title.txt                 # <= 30 characters
    short_description.txt     # <= 80 characters
    full_description.txt      # <= 4000 characters
    video.txt                 # optional http(s) URL
    images/
      icon.png                # 512x512
      featureGraphic.png      # 1024x500
      tvBanner.png
      phoneScreenshots/01.png # <= 8 MiB per file
      sevenInchScreenshots/...
      tenInchScreenshots/...
      tvScreenshots/...
      wearScreenshots/...
    changelogs/42.txt         # release notes
  testers/
    internal.txt              # one Google Group per line
    beta.txt
```

Rules:

- a locale directory that contains any listing file must contain `title.txt`,
  `short_description.txt` and `full_description.txt`; a partial listing cannot silently erase a
  description;
- every image set mentioned in the tree is authoritative: the tool deletes all images of that
  type for that language and uploads the files it found, so removing a screenshot from the
  directory removes it from Play when the edit commits. An empty screenshot directory removes
  every image of that type;
- images must be readable PNG or JPEG. The icon must be 512x512 and the feature graphic
  1024x500; each file is limited to 8 MiB. Play still validates the content and rejects a bad
  image with code 7;
- tester files are `<track>.txt` with one Google Group address per line; blank lines and lines
  starting with `#` are ignored;
- `--metadata-dir` also supplies release notes from `<locale>/changelogs/<versionCode>.txt`.
  Changelogs are optional, and a tree may contain only `changelogs/`;
- the whole tree is validated before the API client is created: a malformed listing, image or
  tester file returns code 2 and no edit is opened.

All metadata calls happen inside the same edit as the upload, so the commit is atomic: if a
listing, image or tester update fails, the edit is deleted and Play keeps the previous metadata.

```
google-play-publisher publish -f app-release.aab -t internal --metadata-dir metadata
```

### `google-play-publisher doctor` — MVP

Runs read-only checks and changes nothing. Without `--aab` only access and the track are
checked; with `--aab` the artifact, signature and manifest identity are checked as well.

| Check | How |
| --- | --- |
| `api` | token and app access (read-only release request) |
| `track` | the track exists; number of releases is reported |
| `artifact` | ZIP with `BundleConfig.pb` and a readable `base/manifest/AndroidManifest.xml`; size and sha256 |
| `signature` | JAR signature present (`META-INF/*.RSA` / `*.EC` / `*.DSA`); absent → code 7 |
| `identity` | manifest `package` and `versionCode`; `--package` must match the AAB, otherwise code 2 |

### `google-play-publisher status` — MVP (read-only)

Shows releases, versions and states on a track. Uses the read-only
`applications.tracks.releases.list` method; no edit is created.

```
google-play-publisher status --package com.example.app [--track production] [--json]
```

### `google-play-publisher pull` — read-only download

Downloads the store presence of an app and recreates a metadata directory in the Play/fastlane
layout accepted by `publish --metadata-dir`. `download` is an alias. The command opens one
read-only edit (`edits.listings.list`, `edits.images.list`, `edits.testers.get`,
`edits.tracks.list`), downloads the images, and deletes the edit without committing anything.

```
google-play-publisher pull --package com.example.app --metadata-dir metadata
```

| Flag | Type | Default | Description |
| --- | --- | --- | --- |
| `--package`, `-p` | string | — | `applicationId`; required |
| `--metadata-dir` | path | — | Target directory; required, must be absent or empty unless `--force` |
| `--track`, `-t` | string | `internal` | Track whose release notes are pulled |
| `--version-code` | int | every release | Version whose notes are pulled; must be on the track |
| `--force` | bool | `false` | Replace a non-empty target after the download and validation succeeded |

The generated tree is the exact input format of `publish --metadata-dir`:

```
metadata/
  en-US/
    title.txt
    short_description.txt
    full_description.txt
    video.txt                    # only when Play has a promo video
    images/
      icon.png                   # singular images keep their conventional name
      featureGraphic.png
      tvBanner.png
      phoneScreenshots/001.png   # numbered in Play display order
      sevenInchScreenshots/...
      tenInchScreenshots/...
      tvScreenshots/...
      wearScreenshots/...
    changelogs/42.txt            # notes of the selected release(s)
  testers/
    internal.txt                 # one Google Group per line
```

Behaviour:

- every localized listing is written with all three required text files; `video.txt` is omitted
  when the listing has no video;
- every image type is listed for every locale that has a listing. Singular image types are
  downloaded at full size (`=s0`, not the preview thumbnail) and keep their conventional file
  name; screenshots are numbered `001`, `002`, … in the order Play returns them, which is the
  display order;
- tester groups are pulled for every testing track that has them; a track without testers is
  skipped, and production tracks are not queried because Play accepts testers only for testing
  tracks;
- release notes come from `--track`: without `--version-code`, notes from every release on the
  track are written for every version code of that release; with `--version-code` the selected
  release must contain that code and only `<versionCode>.txt` is written. A track without
  releases, or a missing track when no version code was requested, produces listings and images
  without changelogs; `--version-code` on a missing track is code 4;
- the download is staged in a hidden sibling directory. The staged tree is parsed by the same
  validator as `publish` before it replaces the target, so an API failure, a malformed listing
  or an invalid image never leaves a partial tree and never touches an existing target;
- a non-empty target is a usage error (code 2) before authentication. `--force` accepts it,
  downloads first, and swaps trees only after validation succeeds. The previous tree is kept
  until the swap.

The command validates `--package`, `--track`, `--version-code`, `--metadata-dir` and the target
state before creating the client, so a local mistake costs no authentication and no edit.
`pull` still creates an edit, so it consumes the daily edit quota and conflicts with a
concurrent run on the same app; it never commits or changes Play.

### `google-play-publisher rollout`

Changes an existing release without uploading a bundle:
`insert → tracks.get → tracks.update → commit`. The release is read inside the edit, so release
notes, name, version codes, in-app update priority and country targeting are preserved; only the
status and the user fraction change.

| Flag | Type | Default | Description |
| --- | --- | --- | --- |
| `--package`, `-p` | string | — | `applicationId`; required |
| `--track`, `-t` | string | `internal` | Track that holds the release |
| `--version-code` | int | — | Release to change; optional when exactly one release matches |
| `--fraction` | float | — | New user fraction, `0 < f < 1`; implies `inProgress`, so it also resumes a halted release |
| `--halt` | bool | `false` | Stop serving the release |
| `--complete` | bool | `false` | Roll the release out to all users |
| `--changes-not-sent-for-review` | bool | `false` | Save changes without submitting them for review |
| `--on-in-review` | enum | `error` | `error` → `ERROR_IF_IN_REVIEW`; `replace` → `CANCEL_IN_REVIEW_AND_SUBMIT` |
| `--dry-run` | bool | `false` | Validate the edit and delete it without committing |

Exactly one of `--fraction`, `--halt` and `--complete` is required; combining them is a usage
error. Without `--version-code` the command changes the single `inProgress` or `halted` release
on the track. When several releases match, it fails with code 2 and asks for `--version-code`
instead of guessing. A version code that is not on the track is code 4.

`--halt` keeps the fraction Play already stores, so a later `--fraction` resumes the rollout from
the same percentage. `--complete` clears the fraction and serves the release to everyone.
`--dry-run` still creates and deletes an edit, which consumes the daily edit quota.

```
google-play-publisher rollout -p com.example.app -t production --fraction 0.2
google-play-publisher rollout -p com.example.app -t production --version-code 42 --halt
google-play-publisher rollout -p com.example.app -t production --version-code 42 --complete
```

### `google-play-publisher promote`

Declares the version codes of a source release as a new release on a destination track:
`insert → tracks.get(source) → tracks.get(destination) → tracks.update(destination) → commit`.
No bundle is uploaded, so promotion works with artifacts that were built for another track.

| Flag | Type | Default | Description |
| --- | --- | --- | --- |
| `--package`, `-p` | string | — | `applicationId`; required |
| `--from` | string | — | Source track; required |
| `--to` | string | — | Destination track; required, must differ from `--from` |
| `--version-code` | int | highest on the source | Release to promote; must be on the source track |
| `--status` | enum | `completed` | `completed` \| `draft` \| `inProgress` (`inProgress` requires `--rollout`) |
| `--rollout` | float | — | Staged rollout fraction; implies `inProgress` |
| `--metadata-dir` | path | — | Play-style metadata tree: listings, images, testers and changelogs applied in the same edit; changelogs require `--version-code` |
| `--release-name` | string | source name | Release name stored in Play |
| `--in-app-update-priority` | int | `0` | Same semantics as `publish` |
| `--country`, `--include-rest-of-world` | | | Same semantics as `publish` |
| `--yes` | bool | `false` | Required when `--to production` |
| `--changes-not-sent-for-review` | bool | `false` | Save changes without submitting them for review |
| `--on-in-review` | enum | `error` | Same as `publish` |
| `--dry-run` | bool | `false` | Validate the edit and delete it without committing |

Selection and data:

- without `--version-code` the release with the highest version code on the source track is used;
  draft releases are ignored, and an explicitly selected draft is rejected with code 2;
- `--metadata-dir` applies listings, images, testers and release notes in the same edit as the
  promotion; a changelog-only tree is accepted;
- release notes come from `<locale>/changelogs/<versionCode>.txt` when both `--metadata-dir`
  and `--version-code` are passed; otherwise the notes of the source release are reused instead
  of silently dropping them. Without `--version-code`, changelog files are ignored because
  promotion has no AAB to select them;
- the release name defaults to the source release name;
- a version code that is already on the destination track is a conflict (code 5) — use `rollout`
  to change its fraction;
- an unknown source release or an empty source track is code 4, and a missing destination track
  (for example a misspelled custom closed track) is code 4 with a hint;
- promoting to `production` is refused with code 2 unless `--yes` is passed. There is no
  interactive prompt: CI must state the intent explicitly.

```
google-play-publisher promote -p com.example.app --from internal --to beta
google-play-publisher promote -p com.example.app --from beta --to production \
  --version-code 42 --rollout 0.1 --yes
```

## 3. Configuration

Priority: flags → defaults. Configuration files are not supported in v0.1 (fewer ways to make
a mistake). Environment variables are limited to Google auth and terminal behavior:

| Variable | Purpose |
| --- | --- |
| `GOOGLE_APPLICATION_CREDENTIALS` | Path to the JSON key (ADC) |
| `NO_COLOR` | Disable color in text logs |

## 4. Exit codes

| Code | Name | When |
| --- | --- | --- |
| 0 | `OK` | Success; also an idempotent no-op (`--if-exists=skip`) and an explicit `--changes-not-sent-for-review` save |
| 1 | `INTERNAL` | Unexpected error/panic, or the uploaded bundle does not match the inspected artifact |
| 2 | `USAGE` | Bad flags, missing file, invalid changelog, incompatible combination |
| 3 | `AUTH` | 401/403: wrong key path, rejected token request, missing permissions, service account not added, API disabled |
| 4 | `NOT_FOUND` | App or track not found, no access to the app, no release to change or promote |
| 5 | `CONFLICT` | Edit invalidated, changes in review (`ERROR_IF_IN_REVIEW`), version code already exists or is already on the destination track |
| 6 | `TRANSIENT` | Network/timeout/5xx after exhausted retries, broken upload, temporary limits (including the daily edit quota), or a commit whose state could not be verified (the edit is kept) |
| 7 | `REJECTED` | Play rejected the changes: signature, version code, release notes, track configuration |
| 8 | `MANUAL_ACTION` | Changes were saved but not submitted for review (automatic fallback, or an observed `NOT_SENT_FOR_REVIEW` release); submit them manually |
| 130 | `INTERRUPTED` | SIGINT/SIGTERM; the edit is deleted best-effort unless a commit was in flight, in which case its state is unknown and the edit is kept |

Rule: the code reflects the **action** a human or pipeline must take, not the HTTP status.
Details are in [05-errors.md](05-errors.md).

## 5. JSON result

Success:

```json
{
  "schemaVersion": 1,
  "ok": true,
  "command": "publish",
  "package": "com.example.app",
  "versionName": "1.0.42",
  "track": "internal",
  "status": "completed",
  "versionCode": 42,
  "sha256": "b1946ac92492d2347c6235b4d2611184...",
  "editId": "0123456789",
  "review": "sent",
  "managedPublishing": "unknown",
  "durationMs": 41230
}
```

Error:

```json
{
  "schemaVersion": 1,
  "ok": false,
  "command": "publish",
  "package": "com.example.app",
  "error": {
    "code": "conflict",
    "exitCode": 5,
    "message": "version code 42 has already been used (HTTP 400)",
    "apiCode": 400,
    "reason": "badRequest",
    "hint": "reload the app state and retry; bump versionCode if it was already used"
  }
}
```

Fields:

| Field | Values |
| --- | --- |
| `schemaVersion` | `1`; bumped on a backwards-incompatible JSON change |
| `versionName` | AAB `android:versionName`, omitted when the manifest has none |
| `review` | `sent` \| `notSent` \| `replaced` \| `skipped` \| `validated` |
| `metadata` | present only with `--metadata-dir`: `{listings, images, testers}` counts of what was applied |
| `managedPublishing` | `unknown` — the API does not expose the flag; not applicable to `internal` |
| `error.code` | stable machine-readable identifier, see the table below |
| `error.exitCode` | mirrors the process exit code for parsers |
| `error.apiCode`, `error.reason` | Play HTTP status and reason when the failure came from the API |
| `ok` | `false` for failures; for exit code 8 the saved release is reported with `ok: true` and `review: "notSent"` |

`error.code` values (independent of Play wording):

| Code | Exit code |
| --- | --- |
| `usage` | 2 |
| `auth` | 3 |
| `not_found` | 4 |
| `conflict` | 5 |
| `transient` | 6 |
| `rejected` | 7 |
| `manual_action` | 8 |
| `interrupted` | 130 |
| `internal` | 1 |

With `--json`, a failed command writes exactly one object to `stdout`. Logs and the final
human-readable error (including its hint, when available) go to `stderr`, so redirecting
`stdout` to `publish.json` does not hide the failure reason from CI logs. The exit code and
JSON schema are unchanged.
`doctor` reports its checks and the `error` object in that single object; an interruption
also keeps exactly one object and returns code 130. When the release was saved but needs
manual submission (exit code 8), `stdout` contains the success object with
`"review": "notSent"`; the action for the operator is on `stderr`.

A commit that Play may have applied but whose state could not be verified is a failure, not a
success: `stdout` contains the error object with `error.code: "transient"`, and the message
names the package, track, version code and edit ID. The edit is kept.

`rollout` and `promote` report the same envelope with `versionCodes` (an array) and an optional
`userFraction`; `promote` adds `from` and, with `--metadata-dir`, a `metadata` object:

```json
{
  "schemaVersion": 1,
  "ok": true,
  "command": "promote",
  "package": "com.example.app",
  "from": "internal",
  "track": "beta",
  "status": "completed",
  "versionCodes": [42],
  "editId": "0123456789",
  "review": "sent",
  "metadata": {"listings": 1, "images": 0, "testers": 1},
  "durationMs": 3210
}
```

Publish results carry `schemaVersion` (currently `1`) in both the success and error objects.
Adding a field is backwards-compatible; removing or changing a field requires a version bump.

`pull` reports its own envelope:

```json
{
  "schemaVersion": 1,
  "ok": true,
  "command": "pull",
  "package": "com.example.app",
  "track": "internal",
  "metadataDir": "metadata",
  "versionCodes": [42],
  "listings": 3,
  "images": 12,
  "changelogs": 3,
  "testers": 2,
  "durationMs": 5120
}
```

`versionCodes` is an array of every version code whose release notes were considered (empty
when the track has no releases). `changelogs` counts the files written, so a release with two
version codes contributes twice.

## 6. Examples

### Local, internal track

```bash
export GOOGLE_APPLICATION_CREDENTIALS=$HOME/.config/google-play-publisher/sa.json
google-play-publisher doctor --package com.example.app
google-play-publisher publish -p com.example.app -f app-release.aab -t internal \
  --metadata-dir metadata --version-code 42 --release-name 1.0.42
```

`metadata/` uses the Play/fastlane layout: `metadata/<locale>/changelogs/42.txt`.

### CI (GitHub Actions excerpt)

The tool only needs the path to the JSON key; how the file gets to the runner is outside the
tool's responsibility.

```yaml
- name: Publish to internal
  env:
    GOOGLE_APPLICATION_CREDENTIALS: /path/to/google-play-publisher-sa.json
  run: |
    google-play-publisher publish \
      --package "$PACKAGE" \
      --aab app/build/outputs/bundle/release/app-release.aab \
      --track internal \
      --metadata-dir metadata --version-code "$VERSION_CODE" \
      --json > publish.json
```

Alternatively, without an environment variable:
`google-play-publisher publish --credentials /path/to/key.json ...`.

Pipeline requirements:

- a `concurrency` group per app (one edit per user; parallel runs are forbidden);
- a service account with release permissions only ("Release to testing tracks" is enough for
  the MVP);
- managed publishing does not affect `internal`; for other tracks disable it or plan a manual
  "Publish changes";
- keep `publish.json` as an artifact (versionCode, editId — for auditing);
- on failure run with `--debug`: secrets never reach the log, so the artifact is safe.

### Production and staged rollout

```bash
# staged production release of a new AAB, limited to two markets
google-play-publisher publish -p com.example.app -f app-release.aab \
  -t production --status inProgress --rollout 0.05 \
  --country DE --country AT --in-app-update-priority 3 \
  --metadata-dir metadata --version-code 42 --release-name 1.0.42
# later: raise the fraction, then finish
google-play-publisher rollout -p com.example.app -t production --version-code 42 --fraction 0.2
google-play-publisher rollout -p com.example.app -t production --version-code 42 --complete
# promote the same build from beta to production instead of rebuilding
google-play-publisher promote -p com.example.app --from beta --to production \
  --version-code 42 --rollout 0.1 --yes
```

## 7. Debug mode

`--debug` (short `-d`) enables **detailed logging to stderr**. It does not change behavior:
not the call sequence, not the timeouts, not the exit code — only the amount of logs.

| What | Normal mode | `--debug` |
| --- | --- | --- |
| Phases (`preflight`, `insert`, `upload`, `track`, `commit`, `cleanup`) and durations | yes | yes |
| `package`, `track`, `versionCode`, `editId`, `sha256`, AAB size | yes | yes |
| HTTP: method, URL, status, duration, size | no | **yes** |
| Request/response headers (except secrets) and correlation id | no | **yes** |
| Request/response bodies (JSON, up to 4 KiB) | error message only | **yes** |
| Resumable upload progress | every 5% | every second: bytes, percent, current chunk |
| Retry decisions: attempt number, delay and cause | no | **yes** |
| Source of every parameter (flag / env / default) | no | **yes** |
| Stack trace for `INTERNAL` | no | **yes** |

JSON bodies are redacted before they are logged. A secret value cut off by the 4 KiB
capture limit or containing escaped quotes is still replaced with `[redacted]`; a body that
cannot be redacted safely is omitted from the log and the original payload is still replayed
unchanged.

Redaction — the log **never** contains:

- `Authorization`, `Proxy-Authorization` and any OAuth tokens;
- JSON key contents (`private_key` etc.); the file path is allowed;
- AAB bytes — size and sha256 only;
- bodies are truncated to 4 KiB, binary bodies are never dumped.

Output rules:

- debug logs always go to `stderr`; `stdout` stays clean — with `--json` it contains exactly
  one object;
- `--log-format=json` + `--debug` produce JSON lines with `DEBUG` level on `stderr`;
- with `--debug`, HTTP exchanges are logged by a wrapper around `http.RoundTripper`: regular
  requests are buffered and restored, `bundles.upload` logs only headers,
  `Content-Range`/`Content-Length` and progress.

Example:

```bash
google-play-publisher publish -p com.example.app -f app-release.aab -t internal --debug
```

```
time=... level=DEBUG msg="config" package=com.example.app (flag) credentials=/path/sa.json (env)
time=... level=DEBUG msg="http request" method=POST url=".../applications/com.example.app/edits" attempt=1
time=... level=DEBUG msg="http response" status=200 duration=412ms bytes=57
time=... level=INFO  msg="bundle uploaded" versionCode=42 sha256=b1946ac9... size=48MB duration=31s
time=... level=DEBUG msg="commit" inReviewBehavior=ERROR_IF_IN_REVIEW changesNotSentForReview=false
```

Acceptance criteria (covered by tests and a demo run):

- the debug log shows every publish HTTP call — `edits.insert`, `bundles.upload`,
  `tracks.update`, `edits.commit` — with method, URL, status, duration and attempt;
- `--debug --json`: `stdout` is valid and contains exactly one JSON object, logs go only to
  `stderr`;
- searching the log finds no `private_key`, `Authorization` or token values;
- enabling/disabling debug does not change the exit code or the call sequence.

## 8. Compatibility

- Backward compatibility of flags and exit codes is mandatory within a major version.
- New flags must have defaults that preserve existing behavior.
- A JSON schema change requires a `schemaVersion` bump.
